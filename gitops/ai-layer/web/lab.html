Your lab environment: a full-fledged platform

This is a full internal developer platform. Have a look at what is running before you start breaking it:

Don't worry if you don't understand what a lot of these are. We'll explain the relevant ones over the course of the workshop. A few highlights, for funsies:

  • Istio ambient mesh encrypts all traffic between containers inside the cluster, automatically.
  • cert-manager issues and renews the TLS certificates that services present (for example the console's HTTPS), so no one mints certs by hand.

  • External Secrets pulls your Datadog keys out of AWS Secrets Manager, so no credential is committed anywhere.

What BurritoBot is made of

BurritoBot is three pieces, all running in a namespace (a folder inside the cluster) called agent:

  • the agent — talks to the AI model. It is run by kagent, a framework for hosting agents on Kubernetes.
  • workshop-mcp, the tool container — a tool is an action the model can ask for, like "send a web request" or "run a command". When BurritoBot does something, this is where it happens.
  • guard-proxy — a checkpoint between the agent and the model. Several of the fixes are switches on it.

The row of badges at the top of the BurritoBot tab shows which controls are on. It starts empty.

How to fix data exfiltration attacks

First, look at what you'll apply:

cat ~/challenges/c1-network-policy.yaml

It is five NetworkPolicies. A NetworkPolicy is a firewall rule for pods: you list what a pod is allowed to reach, and the cluster drops everything else. Here is what each of the five does:

  • agent-egress-allowlist — the default-deny: block ALL outbound traffic from the agent, except to your cluster's own private network. "Default-deny" just means "nothing is allowed unless a later rule allows it."
  • agent-allow-dns — lets the agent look up names (DNS). Without this it cannot resolve any address at all.
  • agent-allow-otel-egress — lets it keep sending traces to Datadog.
  • agent-allow-kagent-egress — lets it talk to kagent, the framework that runs BurritoBot.
  • agent-allow-intra-namespace — lets the agent's own pods talk to each other.

Where is the model? The AI model behind BurritoBot is Amazon Bedrock. The cluster reaches it over a private address inside its own network, not the public internet. So "allow the cluster's private network" is what keeps burrito-ordering working. The partner webhook is out on the public internet, which nothing in the list allows — so the exfil is dropped while the model still works.

That is why it is five policies and not one: the default-deny alone would also cut DNS and the path to the model and break the agent. The four allows put back exactly what it legitimately needs, and nothing else.

Apply it:

kubectl apply -f ~/challenges/c1-network-policy.yaml

Now run the exact same attack again. The request is dropped before it leaves the machine, so the data goes nowhere. Ordering a burrito still works, because the model is reached over the private network the policy allows.

Prove it is the policy, not luck. Run this from inside the tool container. After about six seconds it prints "blocked by the NetworkPolicy":

kubectl -n agent exec deploy/workshop-mcp -- curl -s -m 6 -o /dev/null -w 'exit=%{http_code}\n' https://agenticburn.com/beacon || echo "blocked by the NetworkPolicy"

There is no log line to show you, because a NetworkPolicy drops traffic silently. The proof is that the same request works from your laptop and fails from inside the cluster. The NetworkPolicy badge lights on your BurritoBot tab once the policy is in.

How to fix rogue image deployments

First, look at the policy that is already on your cluster:

kubectl get clusterpolicy restrict-image-registries -o yaml
spec:
  rules:
    - name: validate-registries
      match:
        any: [{resources: {kinds: [Pod], namespaces: [apps, agent]}}]
      validate:
        failureAction: Audit          # <- watching, not blocking. You flip this.
        pattern:
          spec:
            containers:
              - image: "harbor.agenticburn.com/* | ghcr.io/*
                       | docker.io/library/* | registry.k8s.io/*
                       | *.dkr.ecr.*.amazonaws.com/*"

This is a Kyverno ClusterPolicy. Kyverno is an admission controller: a checkpoint in front of the Kubernetes API. Every new container is checked before the cluster accepts it. If the checkpoint says no, the container never starts.

What this policy says:

  • match — look at every Pod in the apps and agent namespaces.
  • pattern — the image must come from one of the five approved download sites listed above.
  • failureAction: Audit — if it does not, log it and let it run anyway. This is why your villain deployed.

The villain lives at docker.io/peopleforrester/..., which is not on the list. The policy noticed. It just was not allowed to say no.

Flip it from Audit to Enforce:

kubectl patch clusterpolicy restrict-image-registries --type=json -p='[{"op":"replace","path":"/spec/rules/0/validate/failureAction","value":"Enforce"}]'

Now run the same attack again. Ask BurritoBot to deploy the same villain. This time the API refuses it before it ever runs, and BurritoBot tells you a named policy rejected it. The Kyverno badge lights on your BurritoBot tab.

Clean up the first one if it is still running: kubectl -n agent delete deploy promo-mascot. Other CNCF projects that do this job: OPA Gatekeeper and Kubewarden. Kyverno's rules are plain YAML, which is why we use it here.

How to fix filesystem snooping

First, see that the attack was noticed. Falco is detection: it watches what running processes do and raises an alert. It has a rule for this exact file, and it fired the moment the recipe was read. You should see at least one line naming the recipe file (if nothing shows, wait ten seconds and rerun):

kubectl -n security logs -l app.kubernetes.io/name=falco -c falco --tail=40 | grep -i "recipe\|sensitive"

Falco's partner, Falco-Talon, responded by killing workshop-mcp, the tool container that ran the command, and Kubernetes started a fresh one. Look at its age: a low number means it was just replaced.

kubectl -n agent get pods -l app=workshop-mcp

But the recipe was already read before the alert fired. Detection is a smoke alarm. You also need something that stops the read.

Now look at the prevention you are about to apply:

cat ~/challenges/c3-kubearmor-policy.yaml

This is a KubeArmorPolicy. KubeArmor puts a check inside the Linux kernel, on the path every file read has to take. What this one says:

  • selector — apply to the agent's tool pod (matched by its app: workshop-mcp label).
  • file.matchDirectories — the recipe directory, /tmp/burrito-data/config/legacy/, and everything under it.
  • action: Block — refuse the read. The process gets an error and no bytes.

Because the check is in the kernel, the agent cannot go around it, cannot see it, and cannot talk its way past it.

Apply it:

kubectl apply -f ~/challenges/c3-kubearmor-policy.yaml

Now run the same attack again. Ask BurritoBot to grep for the recipe once more. It gets nothing back. Prove it from inside the tool container. Even you, with full admin rights, get "Permission denied" now:

kubectl -n agent exec deploy/workshop-mcp -- cat /tmp/burrito-data/config/legacy/secret-sauce-recipe.conf

Notice the Falco alert goes quiet once KubeArmor is blocking: its rule fires on a successful read, and there are no more of those. Prevention and detection answer different questions; you want both. The KubeArmor badge lights when the policy is in.

How to fix denial-of-wallet attacks

This is a denial-of-wallet attack. Nothing broke. Every request was allowed. The damage is the bill.

The controls so far all answer "is this allowed?". Here the answer is always yes. The real question is "how much?", and that needs something that counts.

The fix is a budget cap. It lives in the guard-proxy, the piece the platform puts in front of the model. It keeps a running total of spend and refuses once the total crosses the limit. The check runs before the model is called, so a refused request costs nothing. Turn it on:

kubectl -n agent exec deploy/guard-proxy -- python3 -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8080/toggle?budget=on').read())"

It prints the guard settings; budget now reads true.

# what that does, and what it changes
GET /toggle?budget=on        ->  GUARDS['budget'] = True

# enforced per request, before the Bedrock call:
if GUARDS['budget'] and spend_usd >= BUDGET_CAP_USD:
    refuse()                 # 0 tokens, 0 cost

Now run the same attack again. Send that prompt a few more times. The cap is 10 cents. Once the counter passes it, BurritoBot stops answering and says the kitchen tab is frozen. The cost counter stops moving, because refused requests never reach the model. The Budget badge lights.

See the numbers the proxy has metered:

kubectl -n agent exec deploy/guard-proxy -- python3 -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8080/cost').read())"

How to fix secret leaks in replies

Nothing was broken into. The recipe is in a Kubernetes Secret, which is the right place for it. The agent is allowed to read Secrets in its own namespace, which it needs for real work. You asked it to use an access it already had, and it did.

The fix is output scanning: a check that reads the model's reply before it reaches you and redacts anything that must not be sent. It has a list of patterns for the secret parts of the recipe (the signature, the amounts, and one made-up ingredient) and redacts every match, however BurritoBot words it. Turn it on:

kubectl -n agent exec deploy/guard-proxy -- python3 -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8080/toggle?output=on').read())"

It prints the guard settings; output now reads true.

GET /toggle?output=on        ->  GUARDS['output'] = True

# runs on the response, AFTER the model has been paid for:
#   the reply is matched against the recipe's secret patterns
#   and every match is redacted before it is returned.

Now run the same attack again. BurritoBot still reads the Secret and still tries to tell you. What comes back is redacted. The Output guard badge lights.

Then look at the trace again. The recipe is in it, in full. This guard runs on the way out: the tokens were spent and the secret already went to the model. You are protected; your logs are not. Challenge 6 fixes that with a guard on the way in.

How to fix prompt injection attacks

This is prompt injection. The model gets one stream of text and cannot reliably tell "content to read" from "instructions to follow". You asked it to summarise a document, and the document did the asking. Every agent that reads content it did not write has this problem.

The fix is input scanning: a check on the prompt before it reaches the model. Two checks run here, because they fail differently:

  • Block list — matches known-bad strings. Fast and exact, but blind to new wording.
  • Classifier — a small model trained to spot injection attempts. Catches new wording, but can be wrong in either direction.

Turn it on:

kubectl -n agent exec deploy/guard-proxy -- python3 -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8080/toggle?input=on').read())"

It prints the guard settings; input_blocklist now reads true.

GET /toggle?input=on   ->  GUARDS['input_blocklist']  = True
                           GUARDS['input_classifier'] = True

# both run on the prompt, BEFORE the Bedrock call:
#   blocklist   - known injection strings
#   classifier  - a prompt-injection scanner

Now run the same attack again. Send the ticket back. It is refused before the model sees it, so the cost counter does not move and the trace stays clean. The Input guard badge lights. Compare that with the trace you left behind in Challenge 5: a refused prompt costs nothing and leaks nothing.

How to fix poisoned tool attacks

Every tool comes with a description telling the model what it is for, and the model reads those descriptions as guidance. So whoever writes a tool description gets a say in what the agent does. One tool here carries extra instructions in its description, and the model followed them.

The input guard from Challenge 6 did not catch this because your prompt was clean. The injection was never in what you typed.

First, look at the tools the agent is allowed to use:

kubectl -n agent get agent workshop-agent -o yaml | grep -A 30 'tools:'

This is BurritoBot's configuration (kagent, the framework that runs it, calls this an Agent). Its tools come from two tool servers. Under tools, each server lists which of its tools BurritoBot may call. That list is the tool allow-list. It lives on the cluster, where the model cannot reach it. The second server, evil-mcp, is the one carrying the poisoned tools.

The fix: cut evil-mcp's allow-list down to the one harmless tool. Keep get_weather, drop read_internal_config and apply_optimization. The model can be talked into wanting a tool; it cannot be talked into having one.

kubectl -n agent patch agent workshop-agent --type=json -p='[{"op":"replace","path":"/spec/declarative/tools/1/mcpServer/toolNames","value":["get_weather"]}]'
spec:
  declarative:
    tools:
      - mcpServer:                     # the real BurritoBot tools
          name: workshop-mcp
          toolNames: [get_menu, place_order, ...]
      - mcpServer:                     # the evil MCP shim
          name: evil-mcp
          toolNames: [get_weather]     # <- the two rogue tools are gone

The platform team owns this spec, not the developer who wrote the prompt. The agent pod restarts to pick up the change; give it about 30 seconds. One trap to know: an empty list here means "every tool", not "no tools", so always name the ones you keep.

Now run the same attack again. Ask the same weather question. The poisoned description is still there, and the agent no longer has the tool to obey it with. In the trace, the rogue call is gone. The Tool allow-list badge lights.

How to fix over-privileged credentials

Kubernetes mounts a service-account token into every pod by default. The agent's account was allowed to read any Secret in the namespace, and to list all of them. It only needs one (the recipe). The extra reach is what let it dump the AWS keys and the terminal password.

None of the earlier guards helped, because they sit between the model and its tools. This request went straight to the API server, around all of them. A guard is only worth what it sits in front of.

First, look at the scoped Role you are about to apply:

cat ~/challenges/c8-scoped-role.yaml

This is a Kubernetes Role: a list of which verbs an account may use on which resources. What this one says:

  • deployments, pods, configmaps, services — create/get/list/patch. The agent still needs these for ordinary work (and for Challenges 1 and 2).
  • secrets, resourceNames: [bat-spit-amazing-awesome-sauce] — get that one Secret, by name.
  • No list on secrets — it can no longer enumerate them, and cannot read any other one.

It replaces the broad Role the agent had.

Apply it:

kubectl apply -f ~/challenges/c8-scoped-role.yaml

Now run the same attack again. The list call returns Forbidden, and so does reading the AWS creds or the terminal password. BurritoBot can still fetch the recipe by name, so Challenge 5 still works. The RBAC scope badge lights.

OWASP, a security standards group, calls this Identity and Privilege Abuse (ASI03). Whatever the credential can reach, the attacker can reach. Shrink it to exactly what the job needs.

Try breaking a control and watch it come back

Argo CD keeps this cluster matching what is checked into Git. If something drifts, it puts it back. Try deleting the guard-proxy, the checkpoint in front of BurritoBot's model:

kubectl -n agent delete deploy guard-proxy; kubectl -n agent get deploy guard-proxy -w

It is back within seconds. You have full admin rights here and you still could not keep it deleted. Press Ctrl+C to stop watching.

Three layers stand behind that. BurritoBot's own account is not allowed to delete Deployments at all. An account that is allowed still gets rejected by a Kyverno policy, because only Argo CD may change the things Argo CD manages. And if anything gets past both, Argo CD restores it within seconds. Look at the policy:

kubectl get clusterpolicy block-argocd-drift -o yaml
Some damage is walled off at the infrastructure level no matter what you do (for example, a command that spawns processes forever is stopped by a process limit). This is your own cluster, so break whatever you like.
